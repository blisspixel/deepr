# Product direction evidence

Sequencing note, 2026-09-20: this dated assessment records the September 13 plan.
The [active roadmap](../../ROADMAP.md#active-release-plan) now puts preparation,
temporal learning, perspective and repeated-use evidence before wider authority.
Older future-version assignments below are historical, not current delivery gates.

Deepr's next meaningful release should remain v2.51: establish whether maintaining one expert helps recurring decisions compared with fresh research, static history, and compiled state. The immediate engineering increment is a verifiable blinded review package and an explicit isolated-arm run recipe. Source preparation already has a narrower, unreleased implementation. More provider routes, a new memory backend, or a larger runtime would not answer the product question.

This is a repository review and primary-source research synthesis, not a value experiment. No blind pilot artifacts, answer keys, expert credentials, or model/provider execution were inspected or used. No paid API request was made. External sources were checked on 2026-09-13; an access date is not a publication date. The source set is selective, not a claim of exhaustive market coverage.

## What the README and roadmap get right

The README identifies a specific use: recurring decisions in a changing domain. It separates durable records from demonstrated improvement, gives a complete first consult path, and makes the production paid-dispatch block explicit. The active release plan correctly makes evaluation precede prediction proposals, provider transaction completion, remote observation, and remote control. Its v2.51 exit gate explicitly forbids selecting a winner with one aggregate score. These commitments agree with the method contract's refusal to equate graph size with quality.

The most useful interpretation of "exceptional" is concrete: after a source changes, the expert can answer a related decision correctly, explain the changed position with the right evidence, preserve still-valid knowledge, abstain when necessary, and save enough review effort to justify maintenance. The project has much of the recordkeeping needed to test this. It has not yet established the effect.

Two clarity issues should be corrected in the next documentation pass:

- The active status item groups completed nested-source checks with unfinished assignment binding. `ROADMAP.md:444` describes verification as covering only outer artifacts, while `docs/SUPPORTED_SURFACE.md:194` documents the unreleased source preflight. `docs/design/expert-purpose-and-value-loop.md:385` also still describes source-world preparation as wholly next. Split the remaining work so the project does not keep rediscovering a solved subproblem.
- `docs/APPROACH.md:55` says cumulative understanding "beats one-shot retrieval" under Core thesis. The README correctly states that longitudinal benefit remains unproven. Calling this explicitly a hypothesis would preserve the ambition without making the normative contract sound like an established result.

Path and line references describe the inspected source revision. Concurrent documentation edits may move them.

## Current external evidence and its relevance

The useful lesson from current systems is to distinguish storing memory, delivering it to a later task, maintaining it correctly, and proving that it helped. These are separate operations and failure modes. The following comparisons describe first-party claims and documented capabilities, not independent tests or Deepr feature commitments.

| Official source and date | What it establishes | Lesson for Deepr |
| --- | --- | --- |
| [Letta's Next Phase](https://www.letta.com/blog/our-next-phase/), 2026-03-16 | Letta announced a shift toward Letta Code, git-backed memory files, client/runtime memory operations, and subagents, replacing several older server-side abstractions. | An evaluation framed only around 2025 memory blocks is stale. Borrow inspectability and version history as user benefits; do not infer that Deepr should replace canonical structured state with writable prose. |
| [Letta Agents SDK](https://www.letta.com/blog/introducing-the-letta-agent-sdk/), 2026-08-17 | The SDK presents a persistent agent interface across local, self-hosted, and cloud backends and across clients/machines. | Continuity is increasingly a user expectation. Deepr can make expert identity and evidence continuity clear through its existing host-facing role. Concurrent machine execution is a separate authority problem and remains beyond this pilot. |
| [Evaluating Memory in Production Agents](https://www.letta.com/blog/evaluating-memory-in-production-agents/), 2026-07-28 | Letta's private Context-Bench V2 separates memory usage from memory generation. It tests retrieval/adherence separately from generalization/hygiene using production-inspired memory profiles, synthetic tasks, and model judging. | The maintained versus compiled arms isolate an important distinction: using a good memory and producing a better future memory are different capabilities. Private, vendor-run scores cannot establish Deepr quality or select its default model. |
| [How To Give Your Agent Memory](https://www.langchain.com/blog/how-to-give-your-agent-memory), 2026-06-24 | LangChain describes trace capture, analysis, and durable context updates. Diagnose failures before proposing memory changes. A useful regression may require a code or evaluation fix rather than a new belief. |
| [What is LangSmith?](https://www.langchain.com/resources/what-is-langsmith), 2026-09-07 | LangChain distinguishes pre-release offline evaluation from live monitoring and feedback, and describes reviewed/versioned context alongside traces and annotation workflows. | Keep the frozen pilot separate from operational outcome observations. Both matter, but they answer different questions. The workflow lesson does not require adopting the hosted product. |
| [LangMem Core Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/), undated living documentation, accessed 2026-09-13 | LangMem separates semantic, episodic, and procedural memory and describes foreground/background formation, extraction tradeoffs, and core transformations versus stateful storage integration. | Measure construction and maintenance effort separately from consultation latency. Keep factual evidence, experience observations, and future behavior proposals distinct. Background work changes when overhead occurs; it does not remove it. |
| [Graphiti repository](https://github.com/getzep/graphiti), undated living repository, accessed 2026-09-13 | Graphiti documents temporal validity, source episodes/provenance, incremental updates, and hybrid semantic/keyword/graph retrieval. Temporal storage and source lineage are implementation capabilities, not proof that the returned answer handles late or contradictory evidence correctly. |
| [Graphiti product overview](https://www.getzep.com/platform/graphiti/), undated living page, accessed 2026-09-13 | Zep describes validity and observation timestamps, preserved invalidated facts, temporal context graphs, and a separate managed context service. | Preserve the distinction between when a fact applied and when it became known. Avoid importing headline vendor accuracy or latency numbers into Deepr expectations without an equivalent task and measurement setup. |

The latest dated source in this set is September 7, 2026. Letta's August SDK announcement and July evaluation update are materially newer than its memory-block documentation. No source reviewed establishes that adding autonomous memory writes reliably improves Deepr's domain decisions. That remains an empirical question.

## A concrete next sequence

1. Finish the v2.51 preparation seam. Preserve the existing source preflight and add the reviewed answer-binding design and mechanical verification. Rehearsal checks should exercise changed bytes, swapped cases, duplicate answers, omitted cells, organizer metadata leakage, and later-world contamination using public synthetic fixtures. Never use lexical tests to decide factual support.
2. Freeze one decision-focused expert blueprint, three worlds, 12 acceptance cases, four arm policies, and the rubric before execution. The protocol already specifies the same model, generation settings, source access rules, and context ceilings across arms. Give the arms equivalent evidence opportunity while preserving their intended memory differences. This pilot evaluates local maintained-state value; it should not be marketed as a frontier-vendor comparison.
3. Run the 48 cells only through separately authorized, proven capacity. Keep `$0` provider-marginal execution as the intended lane under the current repository rules. Record construction, maintenance, consultation, failures, and review effort. A `$10` session ceiling does not revise Deepr's no-paid-inference rule or its `$5` active examples limit.
4. Review exact blinded answer packets, freeze labels, then join the organizer mapping. Publish correctness, factual support, false support, false refusal, uncertainty/abstention, stale reuse, retention/transfer, update completion/latency, effort, and cost separately. Twelve cases are a pilot, not a sufficient sample size claim; 48 correlated arm cells are not 48 independent tasks.
5. Choose the next small increment from the failure evidence. If evidence assembly loses a decisive passage, fix that path. If maintenance introduces stale assertions, fix the reviewed update path. If the maintained arm provides no useful advantage, preserve the negative result and improve the experiment or method before expanding autonomy. Prediction resolution can follow as review-required proposals under v2.52.
